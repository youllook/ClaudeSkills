# 降維輸出（Layered Output）

> 來源：Andrej Karpathy 2026-10-02 推文（二手轉述多份一致，原推未直接核對）。
> 他把「讀懂 LLM 輸出」的方式排成四級：STE 文字 → 圖 → HTML 互動頁 → 講解影片。
> 每往上一級，讀者理解成本降一個量級，產出成本升一個量級。

## 選層規則（先選層，再動手）

| 內容形狀 | 最低要到的層 |
|---|---|
| 結論、判斷、待辦 | L1 |
| 流程 > 3 步、依賴關係、架構、時間軸 | L1 + L2 |
| 多維參數、狀態機、「如果 X 變了會怎樣」、要篩選的長清單 | L1 + L2 + L3 |
| 要對外講解、要給非技術決策者自己看懂 | L4（只出分鏡，不做影片） |

不要為了炫技升層。一張表能講清楚，就不要做互動頁。

## L1：受控語言（STE 80% 模式，中文改編）

ASD-STE100 是英文規範（飛機維修手冊用）。中文沒有官方版，以下是改編規則：

1. **結論先行。** 開頭 1～3 句講結論，再講理由。
2. **一句一事。** 程序句 ≤ 30 字，描述句 ≤ 40 字。段落 ≤ 6 句。
3. **程序句用祈使句。** 「執行 X。」不寫「建議可以考慮執行 X」。
4. **情態詞只用三個：能、會、必須。** 禁用「應該、可能、或許、建議考慮、大致上」。
5. **一詞一義。** 同一件事全文用同一個詞。第一次出現的術語，括號給定義。
6. **名詞串 ≤ 3 個。** 「告警設定消費端缺口處置」→ 拆開寫。
7. **數字、日期、單位寫死。** 「近期」→「2027-12-01」。民國年一律轉西元並標註。
8. **砍填充詞。** 「值得注意的是」「事實上」「本質上」「非常」「顯著」一律刪。
9. **主動語態。** 寫出誰做。「已被更正」→「v4 建議書更正了此處」。

### ⚠️ 鐵律：降維不准降證據強度

STE 禁止模糊情態詞，但**不確定性本身是事實**，不能被刪掉。做法是把模糊詞換成**明確狀態標籤**：

| 原文 | ❌ 錯誤降維 | ✅ 正確降維 |
|---|---|---|
| 外部報告估 2027-2028 完工（待驗證） | 2027 完工。 | 完工時間：2027～2028〔單一二手來源，未驗證〕。 |
| 採用 B 方案的機率高 | 採用 B 方案。 | 採用 B 方案〔推論，三項旁證〕。 |

狀態標籤固定用：〔已核實〕〔推論〕〔未驗證〕〔已被取代〕。
改寫不准壓縮證據強度標示。

降維時順手做**一致性檢查**：原文若有已被後續文件更正的說法，標〔已被取代〕並指向新來源，不要默默照抄、也不要默默改掉。

## L2：圖

- **自包含優先：** HTML 內嵌 SVG（報告零外部資源、可印 PDF）。
- **Markdown 文件：** 用 Mermaid（GitHub／Notion 會渲染）。
- 圖只畫**關係**（依賴、流程、狀態轉移、分區）。文字細節留給 L1。
- 顏色有語意就要有圖例；紅綠必須搭配形狀或文字，不能只靠顏色。

## L3：單檔互動 HTML

- 一個 `.html`，CSS/JS 內嵌，無 CDN，雙擊能開，手機能看（≤ 375px 不破版）。
- 只為三種東西做互動：
  1. **狀態機／模擬**：滑桿拖時間，看狀態怎麼變。
  2. **依賴圖**：點節點看細節、看上下游。
  3. **長清單**：篩選、分組。
- 每個互動元件旁邊必須有一行 L1 文字說它在演示什麼。互動頁不是取代文字，是讓文字可驗證。
- 支援深淺色（`prefers-color-scheme`）。
- 檔名：`<原檔名>-reduced.html`，放在原報告旁邊，**不覆蓋原檔**。

## L4：講解影片（只出分鏡）

不實際產影片。輸出：分鏡表（鏡號／秒數／畫面／旁白 STE 句／對應 L3 元件）。
L3 的互動元件通常就是 L4 的畫面素材，錄螢幕即可。

## 審閱紀錄優先（`.pins.json`）

報告旁若有 `<檔名>.pins.json`（Pin4Html 標註），先讀。已 resolved 的標記是用戶的**編輯決定**：
刪掉的段落、改掉的措辭、拿掉的欄位（例如日期欄），降維版**一律不准加回來**，即使原始資料還找得到。
降維是重新排版，不是重新編輯。

## 短報告的目標不是壓縮

原文已經很短（< 3,000 字）時，降維版字數可能持平甚至變多。這時價值在：
- 把「要誰決定什麼」拉成獨立區塊；
- 把散在表格裡的條件做成**決策工具**（例：選方案＋條件 → 能不能做、會不會自動生效、有沒有實測）；
- 把截圖掛到對應的測試步驟上，當證據而不是附錄。
回報時照實說字數沒降，說明換到了什麼。

## 交付流程

1. 讀原文全文（含 `.pins.json`），列出「結論、流程、依賴、狀態機、清單」各在哪。
2. 依選層規則決定每段降到哪層。
3. 先寫 L1 全文（這是骨架），再補 L2／L3。
4. 一致性檢查：比對同資料夾較新的文件，標〔已被取代〕。
5. 產出放原檔旁，回報時附「原文 vs 降維」字數／閱讀時間對照。

## 技術備註

- 含大量 base64 截圖的檔（> 3 MB）內建瀏覽器開不起來。驗證時用佔位圖做一份輕量副本測互動，測完刪掉。
- 嵌圖用「模板＋Python 注入」：模板寫 `{{IMGS}}`，腳本從原檔抓 data URI 填進去，避免把 MB 級字串塞進對話。
